# Test plan — operator-notifications

Members of a workspace learn about customers who need them in two tiers. **On the web**, every workspace page shows the member's attention count (open conversations that are theirs or unassigned with unread customer messages) in the tab title and next to Inbox. A browser where the member turned it on shows one desktop notification per new customer message in a conversation that is theirs or unassigned, while no tab of that workspace in that browser is in focus. **Away from the web** (no tab with a live connection that has been on screen within 10 minutes), the workspace's own bot pings the member's linked Telegram. A ping is due 5 minutes after the wait began. It goes to the assignee, or to every away linked member for an unassigned conversation. The rest of the team is reached at 30 minutes, or at 5 minutes when the assignee cannot be pinged. Pings are combined to at most one per member per workspace per 10 minutes and at most one per conversation per waiting period. Every condition is checked again at send time, and a ping never carries customer text or a contact name. The Telegram link is made once through a single-use, 10-minute connect link (5 per 10 minutes). Nothing a linked member sends to the bot is captured, and a deactivation or a different bot removes the link.

> **Assumptions (autonomous run 2026-10-19 — change any row by editing this file before `implement`):**
>
> - Levels were picked per AC with the default heuristic, as in the assignment-statuses plan. A pure rule is unit. A repository, use case, route, socket or job against the database is integration. A shape both sides agree on is contract. A full user story through the API is e2e. A screen state is component. A user-facing panel flow is e2e-through-UI. Where a task's DoD already names a level for an AC, the plan follows the task.
> - The **Task** column points at the `tasks.json` id that writes the test. Every row is inside one of the 30 tasks. Five rows were not yet in their task's DoD, so the DoD was extended in both `tasks.json` and the task file: T16 (a taken-over bot still sends pings), T17 (QG-1 (g) team reach and the ≤ 60 s timing assertion), T21 (the in-web latency assertion and the listed integrity queries), T23 (the refetch triggers and per-workspace count), T27 (a reopening customer message notifies).
> - **Desktop notifications are not tested in a real browser.** Headless browsers cannot show operating-system notifications. AC-02 is checked by unit tests of the notifier and of the notifications service worker, with the browser's clients and notification interfaces stubbed (T27). The browser flows only check that the desktop card shows its off or not-available state (T29).
> - **Time is a controllable clock everywhere a threshold matters**: the 5- and 30-minute marks, the 10-minute combining spacing, the 10-minute presence window, the 50-second lease, the 10-minute connect-link expiry and its 5-per-10-minutes window, and the hourly notice. Tests move the clock. They never sleep, except where real socket delivery or a real keep-alive timeout is the subject, and there with a bounded wait.
> - The Telegram side is the repo's scriptable fake Bot API. Updates from Telegram are recorded update bodies POSTed to the real webhook route with the per-bot secret, because the fake has no update-injection helper (SAD QG-2).
> - Visual-regression stays N/A, as in the earlier features' plans.
> - Load scenarios cover the three latency / timeliness NFRs that carry a number. Presence freshness, ping volume, pings to non-members, ping content, captured link messages and the connect-link limits carry numbers too, but they are counts, windows and invariants. Integration tests and integrity queries check those, not load.

## Edge cases / error paths

- Start payload with a token of the wrong length, or a campaign payload → expected: not treated as a connect-link start; captured for an unlinked sender, consumed for a linked one.
- Connect-link request while connected in another tab → expected: refused as already linked; the dialog shows connected from the refusal's settings.
- Second Disconnect → expected: answered as done; no signal, no job.
- Request with a non-JSON body type to the connect or disconnect route → expected: refused as unsupported.
- Presence frame with an extra field, a non-boolean screen flag, over 1 KiB or of an unknown type → expected: ignored; the socket stays open.
- Ten presence frames in one second → expected: one write with the last value.
- Tab that opens hidden and never comes on screen → expected: counts away.
- Crashed tab of the same member → expected: its expired lease is deleted on the member's next open.
- Socket closed on deactivation → expected: lease deleted.
- Process dies after the send transaction commits and before the Telegram call → expected: the ping stays as sending and counts like a failed one; nothing is sent twice.
- A rate-limit answer while a later pause is already stored → expected: the later pause is kept.
- Answer job with both recipient fields, or "cannot connect" without a reason → expected: rejected by the payload schema.
- Three answer timeouts → expected: dead letter; a "notifications off" job still clears the removed link's Telegram id.
- Ping chain broken by a crash → expected: the next minute's cron restarts it; the last live link removed → the chain stops and the cron no longer lists the workspace.
- Contact name with a phishing line → expected: never in any ping text (by the builder's input type and by the secrecy scan); shown as plain text in a desktop notification.
- Telegram display name or member name with markup on SCR-16, SCR-13, SCR-14 → expected: rendered as text.
- Clipboard unavailable or refused → expected: Copy hidden; the link stays selectable.
- Start pressed after the dialog was closed → expected: SCR-16 turns Connected live.
- Background re-read of the settings fails → expected: the last state stays, no error shown.
- Logs on the redeem, interception, answer, sweep and send paths → expected: no bot token, connect token or its hash, ping text, display name or message text; the Telegram user id only in the redeem outcome at debug level.
- Database unavailable during a sweep → expected: the sweep fails without sending; the next run decides again from the ledger (fail-closed).
- Rollback of migrations 08 → 01 on a database with links, pings and waiting conversations → expected: every `down` runs cleanly and the schema returns to its earlier shape.

**Cross-workspace isolation (spec §6.1, SAD QG-2):** every new repository method in `notifications` (telegram links, connect links, presence leases, the ping ledger) and the two new `conversations` reads get their own integration test on `twoWorkspacesWithLinks` (two workspaces sharing one account and one Telegram user id) (T6, T8, T9). The sixth controlled exception, *workspaces with a live Telegram link*, is tested to return workspace ids and nothing else (T8). Every new route gets a foreign-workspace test (AC-12, T19), and the Team mark is tested to count only this workspace's links (T20).

## NFR checks without load (presence, volume, integrity)

- **Presence freshness — closed tab, sleep or lost connection → away ≤ 60 s:** a live-socket integration test with a test socket that stops answering the keep-alive → away on the presence predicate within 60 s; a closed socket → away at once (T14). The 50-second lease and its expiry are unit-tested with the controllable clock (T3, T13).
- **Presence freshness — connected but hidden → away ≤ 10 min + 60 s:** a presence frame with the screen flag off → present at 9 min, away at 10 min plus one sweep (T14, T3); the web sends the frame on open and on every visibility change (T22).
- **Ping timeliness ≤ 60 s p95 (CI seed):** in the QG-1 scenarios (a) and (b) the logged due-to-accepted time of each ping is ≤ 60 s, with paused time logged separately (T16, T17).
- **In-web latency ≤ 3 s (CI seed):** a captured customer message's frame reaches a connected socket and the attention route returns the new count within 3 s (T21); the browser flow asserts the title within 3 s (T29). The server logs the time from capture to push per event.
- **Pings to non-members — 0:** the send-time share lock on the membership, tested in both lock orders (T16, T21), and the integrity query below.
- **Ping volume — ≤ 1 per 10 min per member per workspace; ≤ 1 per conversation per period:** QG-1 (b) and (f) (T17), the ledger unique key (T1, T9) and the integrity queries below.
- **Ping content — 0 with message text or contact name:** the builder's input type has no such field and every set shape is unit-tested (T4); the secrecy scan covers every ping text sent to the fake Bot API (T21).
- **Captured link messages — 0:** the webhook interception tests assert unchanged contacts and conversations for every consumed case (T12), plus the integrity query below.
- **Connect link — single use, 10 min, ≤ 5 per 10 min:** AC-05 and AC-13 rows (T4, T10, T11, T19), with the window moved by the controllable clock.
- **Integrity queries (T21), run after every API e2e flow and after the concurrency tests of T11, T16 and T17; each must return no row. The same queries go into the run book (SAD §7, data-model audit):**
  1. pings whose recipient's membership was not active at the ping's creation;
  2. more than one ledger item per member, conversation and waiting period;
  3. two pings to one member and workspace less than 10 minutes apart;
  4. contacts whose Telegram id equals a live link's Telegram user id in the same workspace;
  5. live links whose Telegram bot id differs from the workspace's current bot;
  6. live links of a member whose membership is not active;
  7. a link removed by its member that still holds a Telegram user id more than 1 hour after removal;
  8. open conversations waiting by the shared-inbox marker but with no recorded waiting period.
- **Availability 99.5 % monthly:** verified by the uptime check on the health endpoint (monitoring), not by a test.

## Test data

- Seed strategy: the builders in `apps/api/src/test/fixtures/` extended per `data-model.md` §Test fixtures (T1, T5). `insertConversation` gains `waitingSince` and `waitingStartedBy`, and `insertBot` gains `sendPausedUntil`, all defaulting to none. The new builders are `insertTelegramLink` (live by default, removed variants clear the right columns), `insertConnectLink` (returns the raw token so a test can build the start payload; expiry = creation + 10 min), `insertPresence` (live and on screen by default), `insertPing` (ping and items in one transaction) and `twoWorkspacesWithLinks`, the base of every isolation test and of the other-workspace rows of AC-10 and AC-12. Existing `insertMembership`, `insertReply`, `insertReadMark` and the activity builders set up assignees, sent replies, watermarks and reopens. Synthetic ids, `Test User`, `@example.test` and small Telegram ids such as `5001n` only.
- Telegram updates: recorded-update builders for a connect-link start, a campaign start, text, media and an edit (T12), POSTed to the real webhook route with the per-bot secret. The fake Bot API is scripted per test for accepted, blocked, rate-limited with a retry time, unauthorised and timeout answers (T7), and records every send for the content and secrecy assertions.
- Time: one controllable clock port drives the 5- and 30-minute marks, the 10-minute spacing, the presence window and the lease, the connect-link expiry and limit window, the hourly notice and the 15-minute opened-at window. Sweeps are triggered by running the job at a set clock time, not by waiting for its schedule.
- Integration dependency: an ephemeral real database container per suite with all migrations applied, NOT a mocked store. The job queue lives in the same database. Concurrency tests use separate pooled connections with committed transactions.
- Cleanup boundary: per test. Every test truncates the feature's tables (telegram links, connect links, presence leases, pings and their items, plus the inbox, membership and bot set and the job queue's tables) and resets the fake Bot API script and the clock. API e2e flows reset the database before each flow. Browser flows reset it and close every socket and browser context between flows. Container-backed suites remove their containers and data even on failure (CLAUDE.md §Tests).

## NFR validation (load)

- Ping timeliness p95 ≤ 60 s (due or allowed moment → accepted, paused time excluded) → scenario: 5 workspaces, each with 10 linked away members and a stream of 1 new waiting conversation per workspace every 10 s for 30 min (mixed mine / unassigned / teammate's, about a third reaching the 30-min team mark), against the fake Bot API answering in 50–200 ms; assert p95 due-to-accepted ≤ 60 s from the job timing log, zero server errors, and no row from the integrity queries afterwards.
- In-web latency p95 ≤ 3 s → scenario: 50 connected sockets across the same 5 workspaces, 5 customer messages/s through the webhook route for 5 min; assert p95 from capture commit to the message frame on a socket ≤ 3 s and p95 of the attention route after that frame ≤ 3 s end to end.
- Reply delivery p95 ≤ 2 s with 50 pings due at once on one bot → scenario: 50 linked away members due at the same moment on one bot while 2 replies/s are drained for 5 min; the fake answers one rate-limit with a retry time; assert reply send p95 ≤ 2 s, pings stop for the pause and resume after it, and no reply waits for a ping. A short version (one burst of 50, 60 s) runs in CI against the fake Bot API (T21).
- Tool: the load tool already in your repo, or e.g. k6 or Locust. The first two scenarios run on a production-like host before each release, not on a shared CI runner.
