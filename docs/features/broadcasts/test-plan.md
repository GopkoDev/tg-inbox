# Test plan — broadcasts

A business owner sends one plain-text message from the workspace's own bot to a chosen part of the contact base — a tag audience (any of / all of / no tags, plus tags to leave out) or a hand-picked broadcast group — from the panel. Any member drafts, edits and duplicates; only a business owner launches, against exactly the version and the reachable set the confirmation showed, at most 10 times per 24 hours, and stops. The recipient list is frozen at launch, each recipient is sent at most once (a send with no answer is never repeated), sending stays at or below 25 per second per bot, waits for the send pause and never delays replies, and the live delivery report gives every recipient a truthful outcome. tg-inbox learns from Telegram who blocked the bot, per Telegram bot, and every delivered broadcast shows as a broadcast item in the recipient's thread without touching conversation state. Nothing crosses a workspace.

> **Assumptions (autonomous run 2026-10-23 — change any row by editing this file before `implement`):**
>
> - Levels were picked per AC with the default heuristic, as in the contacts and operator-notifications plans. A pure rule (the text and name rule, the status machine, permissions, the fingerprint, the outcome map, the fixable set, the turn picker) is unit. A repository, use case, worker, route or the live socket against the database is integration. A shape both sides agree on (the shared schemas against `contracts/openapi.yaml` and `contracts/events.md`) is contract. A full user story through the API and the fake Bot API is e2e; through the browser it is e2e-through-UI. A screen state from `screens.md` is component.
> - The **Task** column points at the `tasks.json` id that writes the test. Every row sits inside one of the 40 tasks; where a task's DoD did not yet name a placed test, the DoD was extended in both `tasks.json` and the task file: T8 (the same Telegram bot reconnected), T22 (no item for failed, stopped and blocked), T23 (duplicates with no working bot), T24 (two workspaces' links at once), T27 (removal leaves the contact, frozen recipients after retags and unblocks, only the text sent, a linked member never a recipient), T28 (report live update and another workspace's latency) and T30 (the guard landings).
> - The audit's code findings are pinned by tests: capture writes the reach row for the receiving Telegram bot and an older message does not clear a newer block (T7); a block fact older than `changed_at` is ignored (T7); the thread's keyset places `broadcast` after `activity` (T13); 10 000 recipients insert in one set-based statement within the launch budget (T15, T28); recipient positions follow the fingerprint's order (T20).
> - Concurrency is tested with separate pooled connections and committed transactions (two launches of one draft, two launches racing for the 10th slot, two claimers of one recipient, a stop racing a claim, two members' group adds and removes, a deactivation racing a launch), never by mocking a lock.
> - Telegram is the repo's scriptable fake Bot API: it records every `sendMessage` with its time and bot, and can answer a send with success, a rate limit with `retry_after`, "blocked by the user", "user is deactivated", "chat not found", a text refusal, another error, a delay, or no answer. "Killed mid-send" is simulated by ending a link between its claim commit and its outcome (the next link then runs), not by killing the test process.
> - Time: a controllable clock port for the 24-hour cap, the 1-second report coalescing and the 48-hour measure in unit tests; integration tests write `launched_at` / `claimed_at` values directly instead of waiting. The pace and completion checks (T28) use real time against the fake's answer delay.
> - Visual-regression stays N/A, as in every earlier feature's plan.
> - Load scenarios cover the spec §6 rows that carry a latency, throughput or time number. The rows that are counts and invariants (at most once, frozen recipients, launch cap) are checked by integration tests and integrity queries (§NFR checks without load), not by a load tool.

## Edge cases / error paths

- A save body with neither name nor text, or a name and a text both invalid → expected: refused as invalid input naming the field; nothing written.
- A tag audience naming the same tag as chosen and left out → expected: refused as invalid input.
- A tag id of another workspace in a tag audience → expected: refused as the tag not found; nothing written.
- A group add, add-all-matching or remove on a draft a teammate switched to a tag audience → expected: adds refused as a changed draft with the current draft; a remove answered as unchanged.
- A group remove of a contact not in the group (or of another workspace) → expected: answered as unchanged, with no hint about foreign ids.
- A repeated delete of the same draft → expected: not found (idempotent by state).
- A repeated stop → expected: answered as unchanged.
- A duplicate choice that does not fit the source (same tags for a group broadcast, all recipients for a draft) → expected: refused as invalid input naming the audience.
- A draft whose text is empty at launch → expected: the confirmation and the launch refuse it with the text message.
- A launch with a version or fingerprint in the wrong shape → expected: refused as invalid input; nothing launched.
- A `my_chat_member` update for a group chat, a channel or the bot's own status → expected: ignored; no reach change.
- A `my_chat_member` update for a Telegram user who is not a contact (for example a linked member) → expected: no-op.
- The same block notice delivered twice → expected: the second changes nothing and publishes nothing.
- A link that throws three times → expected: the dead letter logs the workspace id and queues a fresh link 60 seconds later; sending resumes.
- A link that runs past its 20-second budget → expected: no new claim after the budget; its successor continues.
- A bot answer in the 400 range that is not a known chat-level description → expected: classified as a text refusal and the broadcast aborts (sad.md §11 risk), logged by code and description class only.
- An older browser tab that does not know the new frames → expected: the frames are ignored and the socket stays open; the next read shows the change.
- A background re-read on the report or the list fails → expected: what is shown stays; the next frame or resync asks again.
- The broadcast text, a broadcast name, a contact name or a username with markup → expected: rendered as text everywhere and sent with no formatting mode.
- Logs, frames, signals and job payloads on every broadcasts path → expected: ids, counts, states and reasons only; never the text, a name, a username or a chat id; the picker's search text masked in request logs.
- Rollback of migrations 08 → 01 on a database with broadcasts, recipients, items and reach rows → expected: every down runs cleanly and the schema returns to its earlier shape; re-applying restores the backfill (re-runnable without duplicates).

**Cross-workspace isolation (spec §6.1, SAD §8):** every new repository method in `broadcasts` (broadcasts, audience tags, group rows, recipients), in `contacts` (reach rows, audience evaluation) and in `conversations` (broadcast items) gets its own integration test on `twoWorkspacesWithBroadcasts` (T7, T8, T13, T14, T15); every broadcasts route and the two changed inbox reads get a foreign-workspace case (T25, T26); the e2e tenancy suite names foreign broadcast, contact and conversation ids on every write and checks that a link only sends its own workspace's recipients through its own bot (T27). No new controlled tenancy exception exists, so none is tested.

## NFR checks without load (counts and invariants)

- **At most once per recipient — 0 recipients sent the same broadcast twice:** two concurrent claimers of one recipient (T15), concurrent launches (T20), a link ended between claim and outcome then the next link (T22), an unanswered send never resent (T22), a restart mid-send (T24); integrity query 1 below after every e2e story.
- **Frozen recipients — 0 changes to a launched broadcast's text or recipient list:** one test per edit path on a launched broadcast (T16, T18, T27), the recipient rows unchanged after retags, new customers and unblocks (T27); integrity queries 3 and 5.
- **Launch cap — ≤ 10 launches per workspace per rolling 24 h:** the 11th refused with stopped and aborted launches counted, two launches racing for the 10th slot (T20); integrity query 4.
- **Tenant isolation — 0 group rows or recipients naming another workspace's contact:** the composite keys (T3), the isolation suite (T7, T8, T13–T15, T26, T27); integrity query 6.
- **Items match outcomes — 0 delivered or not confirmed recipients without a broadcast item, 0 recipients with two items:** T13, T22; integrity queries 2 and 7.
- **Availability 99.5 % monthly:** verified by the uptime check on the health endpoint (monitoring), not by a test.
- **Integrity queries (`broadcastIntegrity.*` in the e2e helpers, T27), run after every API e2e story and after the concurrency tests of T15, T20 and T22; each must return no row. The same queries go into the run book (SAD §8):**
  1. recipients still `sending` with no active link of their workspace (the e2e stories also assert on the fake Bot API's record that no recipient was sent the same broadcast twice);
  2. recipients with more than one broadcast item;
  3. launched broadcasts whose recipients were created after `launched_at`;
  4. workspaces with more than 10 launches in any 24 hours;
  5. launched broadcasts whose `recipient_count` differs from their recipient rows;
  6. recipients or group rows whose contact belongs to another workspace;
  7. delivered or not confirmed recipients without a broadcast item for their contact's conversation.

## NFR validation (load)

- Broadcast pace per bot ≤ 25 messages per second over any 1 s window → scenario: two broadcasts of one workspace (3 000 recipients each) sending together for 2 minutes against the fake with a 50 ms answer delay; assert the maximum number of broadcast sends of that bot in any sliding 1 s window ≤ 25.
- Broadcast completion → scenario: one broadcast of 1 000 recipients with a 150 ms answer delay and no rate-limit answers; assert every recipient has an outcome ≤ 90 s after launch. Pre-release: 10 000 recipients, assert ≤ 10 minutes.
- Reply latency during a broadcast p95 ≤ 2 s → scenario: a 10 000-recipient broadcast sending while operators send 2 replies per second for 5 minutes; assert p95 from reply send to Telegram accepted ≤ 2 s, and no reply refused or delayed by the send pause.
- Cross-workspace isolation of load → scenario: workspace A sends 10 000 while workspace B sends 2 replies per second and its ping sweep runs; assert B's reply and ping p95 within 1 s of the same run with A idle.
- Draft audience count p95 ≤ 500 ms → scenario: on the load seed, 10 draft reads per second for 5 minutes, half a tag audience (any / all / none with a left-out tag), half the 10 000-contact group; assert p95 server time ≤ 500 ms per kind.
- Launch p95 ≤ 2 s → scenario: 20 launches freezing 10 000 recipients each, re-seeding between them; assert p95 from confirm to sending ≤ 2 s.
- Report live update p95 ≤ 3 s → scenario: during the completion scenario, 20 sockets of the workspace connected; assert p95 from an outcome's commit to the report's re-read showing it ≤ 3 s.
- Blocked state freshness p95 ≤ 5 s → scenario: 100 block and unblock notices posted to the webhook over 1 minute; assert p95 from receipt to the reach row changed and the signal published ≤ 5 s.
- Stop takes effect → scenario: stop a 3 000-recipient broadcast after 1 200 outcomes; assert 0 sends of it recorded with a start time more than 2 s after the stop's commit.
- Tool: the load tool already in your repo, or e.g. k6 or Locust. These run on a production-like host before release; a single-run version of each (one window, one 1 000 run, one interleaved reply batch, one draft read per kind, one launch, one stop, one block notice) asserts the same thresholds in CI as part of T28.
