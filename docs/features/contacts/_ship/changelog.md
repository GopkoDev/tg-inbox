# Changelog — contacts

## contacts — the Contacts list and the contact profile on real data, workspace tags any member adds from the inbox or the profile, and an owner-only Settings — Tags to rename, merge and delete them

**What:** The two preview screens now show real data, and contacts get workspace tags. Operators and business owners of a workspace have the same rights over contacts and over tagging a contact; only managing the tag list is owner-only.

- **Contacts list.** Every contact of the workspace, newest "last wrote" first (the send time of the contact's own messages; team replies never count), 50 at a time with Show more continuing from the last contact shown. Each row shows the name, username, tags in tag-list order, language, first and last wrote; a missing username or language shows "none". The page says how many contacts there are and how many match. The sample data and the "Sample data" label are gone.
- **Search and tag filter.** Search follows the inbox rules (anywhere in the full name or username, any letter case, a leading "@" ignored). The filter keeps contacts carrying *any of* or *all of* the chosen tags, or contacts with *no tags* (a mode of its own). Search and filter live in the page address, so reload, back and a saved link open the same view; a renamed tag still filters under its new name, and a tag that no longer exists is dropped with a notice. The count is the size of a future broadcast segment.
- **Contact profile.** The facts Telegram gave us, the tags with who added each one and when, the tag history (added, removed, merged, removed by a delete, under the name the tag had then, newest first), and the contact's one conversation: status, assignee, the "waiting for a reply" marker and Open in inbox. Its history tab is the conversation thread, read-only and live, with media through the panel. **Reading it never marks anything read**: unread counts, the attention count and pings stay as if the profile had not been opened, and there is no reply box.
- **Tagging.** The tag control sits on the profile and on the inbox conversation header (the contact's name there links to the profile). Typing offers existing tags first (starting-with before containing); "Create tag "Kyiv"" is a separate, named choice shown only when no tag has that name ignoring case and spacing. A tag name is stored tidied (ends trimmed, inner spaces collapsed, zero-width spaces removed), 1–32 characters as a person sees them; names that differ only in letter case, spacing or invisible joiners are the same tag. Limits: 100 tags per workspace, 20 per contact, 60 tag changes per member per minute. One line of guidance says tags are visible to the team and must not record sensitive traits. A teammate's change shows live on every open profile and conversation header.
- **Settings — Tags (owners only).** Every tag with its contact count (the count opens the filtered list), in dictionary order ignoring case. Rename; renaming into an existing name offers a merge (the merged contacts keep the earlier addition, each gets a "merged into" history entry); delete states how many contacts lose the tag and refuses if that number changed meanwhile. An operator sees no Tags section and gets the owners-only card on its address.
- **Honest races.** Picking a tag an owner has just deleted or merged says it no longer exists and shows the current tags; picking one that was renamed adds it under its new name. A contact never carries a tag outside its workspace's tag list.

**Why:** Pilot workspaces collect contacts every day since the inbox shipped, but the team could only see a customer as a name on a conversation, and the pitch to pilots is tagging as "your broadcast base in the making" ([spec](../spec.md) §1; idea brief §7). Roadmap step 8 (broadcasts) selects recipients by tag, so every week without tags is a week of customers to tag after the fact. Key decisions:

- [ADR-0001](../adr/0001-own-tags-in-the-contacts-module-with-its-own-routes-and-compose-the-profile-conversation-from-inbox-reads.md): tags are owned by the `contacts` module with its own routes; the profile's conversation is composed from `inbox` reads.
- [ADR-0002](../adr/0002-identify-tags-by-a-stable-id-and-keep-them-unique-by-a-normalised-name-key-computed-in-the-domain.md): a tag is identified by a stable id and kept unique by a normalised name key computed in the domain (one shared function for the server and the picker).
- [ADR-0003](../adr/0003-record-every-contact-tag-change-as-an-append-only-history-entry-with-the-tag-name-at-that-moment.md): every contact tag change is an append-only history entry carrying the tag's name at that moment.
- [ADR-0004](../adr/0004-serialise-tag-writes-under-a-per-workspace-tag-lock-and-recheck-a-delete-against-the-confirmed-count.md): tag writes are serialised under a per-workspace tag lock, and a delete is re-checked against the confirmed count.
- [ADR-0005](../adr/0005-keep-first-and-last-customer-send-times-on-the-contact-written-by-capture.md): first and last customer send times are kept on the contact, written by capture.
- [ADR-0006](../adr/0006-read-the-profile-conversation-through-the-existing-inbox-reads-that-never-mark-read.md): the profile's conversation is read through the existing inbox reads that never mark read.
- [ADR-0007](../adr/0007-signal-tag-changes-as-contact-changed-per-contact-and-tags-changed-per-workspace.md): tag changes are signalled as `contact.changed` per contact and `tags.changed` per workspace.

**How to use:** In the panel open *Contacts* (search, filter, Show more, choose a contact), a contact's profile (tags, tag history, conversation, Open in inbox), the tag control on the profile or the inbox conversation header, and, as a business owner, *Settings — Tags*. The HTTP surface is in [openapi.yaml](../contracts/openapi.yaml):

- `GET /api/workspaces/:workspaceId/contacts` — the list page (search, `mode` any / all / none, tag ids, keyset cursor, matching and total counts).
- `GET /api/workspaces/:workspaceId/contacts/:contactId` — the profile; `GET …/contacts/:contactId/tag-history` — its history pages.
- `POST /api/workspaces/:workspaceId/contacts/:contactId/tags` — add an existing tag or create-and-add by name; `POST …/contacts/:contactId/tags/:tagId/remove` — remove one. A carried add or a missing remove answers 200 `unchanged`.
- `GET /api/workspaces/:workspaceId/tags` — the tag list with counts; `POST …/tags/:tagId/rename` (a merge needs the confirmed target) and `POST …/tags/:tagId/delete` (with the confirmed count) — business owners only.
- `GET /api/workspaces/:workspaceId/inbox/contacts/:contactId/conversation` — the contact's conversation summary for the profile; its thread uses the existing read routes.
- Refusals: eight new error codes (declared in `packages/shared/src/errors.ts`), including the 60-per-minute tag change limit (429 with the retry time), the name taken (with the holder's count, for the merge offer) and the count changed (with the current count).
- Live: two new frames on the `GET /live` socket, `contact.changed` and `tags.changed` (ids only), see [events.md](../contracts/events.md). Tabs opened before the deploy ignore them and catch up on their next read.

**Operational notes:**

- **Migrations:** six reversible migrations, `1791681110006_add_contacts_wrote_times` … `1791681110011_create_contact_tag_history` (first and last wrote on `contacts`, their gap-safe backfill, the list indexes, `tags`, `contact_tags`, `contact_tag_history`; see [data-model.md](../data-model.md)). Run `pnpm db:migrate` on deploy before the new API starts; nothing else is operational.
- **Rollback:** revert the deploy, then `pnpm db:rollback` six times. This drops every tag, contact tag and tag history entry and the first / last wrote columns (contacts, conversations and messages stay).
- **Jobs (pg-boss):** none new. **Tenancy:** no new controlled exception; every cross-entity link is a composite FK that carries `workspace_id`, so a contact cannot carry another workspace's tag.
- **Config:** no new keys (`apps/api/src/platform/config.ts` and `.env.example` are unchanged on this branch). **Feature flag:** none. Tags never reach Telegram, so tagging works in every bot state.
- **Logs:** tag logs carry ids and outcome codes only, never tag names, contact names or usernames; every merge emits a `tag.merged` event (workspace, merged tag, target tag, actor) for the look-alike merge alert (spec §7).
- **Run-book integrity queries:** the four queries in `sad.md` §7 / `test-plan.md` (two tags with one name key, workspaces over 100 tags or contacts over 20, contact tags crossing workspaces, contact tags with no matching history entry) — all expect 0 rows; implemented as `contactIntegrity.*` in `apps/api/src/e2e/helpers.ts`.
- **Residual notes from the review:** the inbox thread cursor has the same crafted-cursor → 500 gap fixed here for the contacts cursors (pre-existing, out of scope); the owner merge of one tag on 10 000 contacts (≤ 2 s) passes alone but timed out once under the full parallel suite on a loaded machine and is worth re-measuring on an idle host; the change-route timing test in `inbox/http/changes.int.test.ts` is a known pre-existing flake under full-suite load.
- **Not yet done:** the spec §6 load scenarios (p95 at 10 000 contacts) run on a production-like host before release; CI runs the single-run versions. Contact deletion and tag exclusion stay open (spec OQ-2, OQ-1).

**Acceptance criteria delivered:** AC-01 – AC-15 — the list (AC-01), search and the any / all / no tags filter in the address (AC-02), the empty states (AC-03), the profile and its tag history (AC-04), reading the profile never marks read (AC-05), tagging from the inbox and the profile, live (AC-06), the name rules (AC-07), one tag per name and the 100 / 20 limits (AC-08), owner rename, merge and delete (AC-09), Settings — Tags with counts (AC-10), the owner-only refusal (AC-11), access control and tenancy (AC-12), tags across renames, bot states and workspaces (AC-13), deleted, merged or renamed tags in an open picker (AC-14), the 60-per-minute limit (AC-15).
