# tg-inbox — working rules

Shared Telegram inbox for small businesses: a business bot per workspace, a web panel for operators.
The decided architecture lives in `docs/architecture-map.md` (+ ADRs in `docs/adr/`); this file is
the short version. When they disagree, the map wins — fix this file.

## Layout

- `apps/api` — Fastify 5 + grammY + Kysely on Node 26 (modular monolith)
  - `src/deps.ts` — `buildDeps(config)`, the shared dependency builder (db, clock, `auth` + `workspaces` repos + `contacts` → `conversations` → `bots` core → `notifications` (links, presence, pings; reads `bots` only through `pingReadiness` + `inboxStatus`) → the `bots` inbound interceptor + bot-connected hook → `team` (built last of these: its `onMembershipDeactivated` port is `conversations.unassignDeactivatedMember` then `notifications` `removeLinkOnDeactivation`; `linkedAccounts` feeds the Team `telegram_pings` mark) → `inbox` use cases incl. `changeState` → the `contacts` reads, tag writes and tag admin (`contactReads`, `tagWrites`, `tagAdmin`) → `broadcasts` (built after `team` and the contacts reads: contacts, conversations, bots and workspaces through their app layers; `inbox` reads `broadcasts.itemDetails` through a closure; `contacts.currentBot` and the `bots` block port are late-bound runtime edges), `destroy()`); no Fastify import, also used by the admin CLI
  - `src/app.ts` — `buildApp(config)`, the composition root: calls `buildDeps()`, registers plugins and every module under `/api` (`/health` stays at root), the realtime listener + live hub (`@fastify/websocket`), and the pg-boss queues/workers (`bots.schedule-health-checks`, `bots.check-health`, `inbox.deliver-replies` + DLQ `inbox.deliver-replies-dlq`, `notifications.send-bot-message` + DLQ, `notifications.send-pings`, `notifications.schedule-pings`, `broadcasts.send` + DLQ `broadcasts.send-dlq`, `broadcasts.measure-blocked-share`; `deps.bindNotificationJobs(boss)` late-binds the senders); with `WEB_DIST_DIR` set it serves the built SPA from the same origin (HTML `GET` fallback to `index.html`, unknown `/api/*` stays a JSON 404)
  - `src/platform/` — config, db, errors, ids, logger, jobs (pg-boss), telegram, realtime (`publish(trx, signal)` = in-transaction `pg_notify` on channel `realtime`; `startRealtimeListener` = one dedicated `LISTEN` connection, reconnect + gap resync)
  - `src/modules/<m>/{domain,app,infra,http}` — one module per roadmap capability: `auth`, `workspaces`, `bots` (token, webhook, health, `my_chat_member` block notices, `sendBroadcastMessage` + the broadcast pacer; the only module that talks to Telegram), `conversations` (capture, list/thread reads with lenses, conversation state + activity entries, replies + delivery bookkeeping, broadcast items (`broadcast_items`, thread kind `broadcast`); app layer only, its routes are served by `inbox`), `contacts` (customers from their Telegram profile + tags: routes `GET …/contacts` (search, `mode` any / all / none + `tag` filter, keyset `after`), `GET …/contacts/:contactId`, `GET …/contacts/:contactId/tag-history`, `POST …/contacts/:contactId/tags`, `POST …/contacts/:contactId/tags/:tagId/remove`, `GET …/tags`, owner-only `POST …/tags/:tagId/rename` (merge with `merge_into_tag_id`) and `POST …/tags/:tagId/delete` (`expected_count`), plus `GET …/inbox/contacts/:contactId/conversation` served via `inbox`; owns `contacts` (incl. `first_wrote_at` / `last_wrote_at`), `tags`, `contact_tags`, `contact_tag_history`, `contact_bot_reach` (per-bot wrote / blocked; `blocked_since` on the list and the profile; audience evaluation for broadcasts)), `notifications` (member's Telegram link, connect links, presence leases, pings: routes `GET …/notifications/settings`, `POST …/notifications/telegram/connect-link`, `DELETE …/notifications/telegram`, plus `GET …/inbox/attention` served via `inbox`; owns `telegram_links`, `connect_links`, `tab_presences`, `pings`, `ping_items`), `inbox` (operator inbox routes under `/api/workspaces/:workspaceId/inbox/…`: list (status + assignee lenses), thread (messages, replies, activity entries, broadcast items + `GET …/conversations/:conversationId/broadcast-items/:broadcastItemId`), mark read, assign / unassign / close / reopen, active members, send / resend reply, media stream, bot status; the live socket + hub in `infra/hub.ts`; the `inbox.deliver-replies` drain worker in `infra/jobs.ts`; owns no tables), `broadcasts` (drafts, tag audience or hand-picked group, launch, sending chain, report, duplicate: routes under `/api/workspaces/:workspaceId/broadcasts…` — `GET` / `POST …/broadcasts`, `GET …/broadcasts/:broadcastId`, `POST …/:broadcastId/{save,audience,delete,duplicate}`, `GET …/:broadcastId/group` (+ `/membership`, `/matching`), `POST …/:broadcastId/group/{contacts,contacts/:contactId/remove,add-matching}`, owner-only `GET …/:broadcastId/launch-confirmation`, `POST …/:broadcastId/{launch,stop}`, `GET …/:broadcastId/recipients`; the `broadcasts.send` chain + `broadcasts.measure-blocked-share` workers in `infra/jobs.ts`; owns `broadcasts`, `broadcast_audience_tags`, `broadcast_group_contacts`, `broadcast_recipients`). Dependencies are one-way: `inbox → {conversations, contacts, bots, workspaces, notifications, broadcasts}`, `broadcasts → {contacts, conversations, bots, workspaces}`, `notifications → {conversations, workspaces, bots}` (app layer, through ports built in `buildDeps()`), `bots → conversations → contacts`, `bots → contacts`, `contacts → workspaces` (member display names)
  - `migrations/` — Kysely migrations (kysely-ctl)
- `apps/web` — React 19 + Vite SPA, Tailwind + shadcn/ui (`src/shared/ui`), Zustand stores per feature
- `packages/shared` — zod schemas, DTO types and error codes shared by api + web

## Rules

- **Module wiring:** each module exports `register<Module>(app, deps)` from `modules/<m>/http/routes.ts`; only `buildDeps()` constructs module dependencies (shared by `buildApp()` and the CLI) and only `buildApp()` registers modules. No self-registration, no globals.
- **Layers:** `domain` (pure, no I/O) → `app` (use cases, ports) → `infra` (Kysely repos, Telegram adapters) → `http` (routes, zod schemas). Imports flow inward only.
- **Cross-module:** call the other module's **app layer** (passed in via the composition root). Never query another module's tables. Async work → pg-boss queue `<module>.<job>`; live updates → `platform/realtime` signals published inside the writing transaction (ids only), fanned out by the `inbox` hub.
- **Errors:** throw `ValidationError` / `NotFoundError` / `ForbiddenError` / `ConflictError` / `UnauthenticatedError` / `TooManyRequestsError` (or a specific-code subclass such as `InvalidCredentialsError`) from `src/platform/errors.ts`. `TelegramUnavailableError` (503) is the one 5xx `AppError`: an upstream failure, logged by code only. The one error handler returns `{ "error": { "code", "message", "details"? } }`; codes are declared in `packages/shared/src/errors.ts`.
- **Conversation state:** `conversations` owns `status` (open / closed), `assignee_account_id`, `state_version` and `customer_message_seq` on the row, and the `conversation_activities` table (kind + cause + actor, thread position time, `activity` signals). Every change goes through `changeAssignee` / `changeStatus` (`conversations/app/state-changes.ts`): lock the row, compare the client's `state_version`, close reasons against the close snapshot, per-member limit (60 per 60 s, advisory lock `changes:<ws>:<account>`), write, activity entry, signal. Routes (`inbox`): `POST …/conversations/:id/{assign,unassign,close,reopen}`, `GET …/conversations/:id`, `GET …/conversations/:id/activities/:activityId`, `GET …/inbox/members`. `workspaces` declares `onMembershipDeactivated(tx, …)`, filled in `buildDeps()`; deactivation unassigns inside its transaction. Codes: `CONVERSATION_STATE_CHANGED`, `CLOSE_NEEDS_CONFIRMATION`, `ASSIGNEE_NOT_ACTIVE`, `CHANGE_LIMIT_REACHED`. Lock order: reply writes take the `drain:` advisory lock first; member changes take memberships (`FOR SHARE`, `lockActiveMembers`) then the conversation row; the workspace row lock is `FOR NO KEY UPDATE`. No new tenancy exception.
- **IDs:** UUIDv7 from `newId()` (`src/platform/ids.ts`), never DB defaults. Telegram ids are `bigint` columns, never primary keys.
- **Tenancy:** every tenant-owned table has a non-null `workspace_id`; every repository method takes `workspaceId` and filters by it. Every repository gets an integration test proving cross-workspace isolation. Six reads are the controlled exceptions because they produce the workspace id: three in `workspaces` (memberships of an account, invitation by token hash, membership for the guard — account id + workspace id from the URL) and two in `bots` (_bot by webhook id_, scoped by possession of the webhook secret's hash; _bots due for a health check_, used only by the scheduled job — bot-connection ADR-0007) and one in `notifications` (_workspaces with a live Telegram link_, workspace ids only, used only by the `schedule-pings` backstop — operator-notifications ADR-0005); a new exception needs a change to the SAD (shared-inbox added none).
- **Contacts & tags:** `contacts` owns tags (≤ 100 per workspace, ≤ 20 per contact, unique per workspace by name key = tidied name case-folded; one rule in `packages/shared/src/tag-name.ts`, 1–32 graphemes) and the append-only `contact_tag_history` (added / removed / merged / deleted, member + source + name snapshot). Members add (picking or creating) and remove tags; only owners rename, merge (rename into a taken name) and delete. Member changes: 60 per 60 s per workspace (advisory `tag-changes:<ws>:<account>`); owner actions are not counted. Lock order (ADR-0004): advisory `tags:<ws>` (create / rename / merge / delete) → tag rows `FOR UPDATE` in id order (owner) or the contact row `FOR NO KEY UPDATE` (member) → `tag-changes:` lock → tag row `FOR KEY SHARE` → writes. Signals `contact.changed {workspace_id, contact_id, change:'tags'}` and `tags.changed {workspace_id}` reach every socket of the workspace. Codes: `TAG_NAME_INVALID`, `TAG_LIMIT_REACHED`, `CONTACT_TAG_LIMIT_REACHED`, `TAG_NOT_FOUND`, `TAG_NAME_TAKEN`, `TAG_MERGE_TARGET_CHANGED`, `TAG_COUNT_CHANGED`, `TAG_CHANGE_LIMIT_REACHED`. Nothing in contacts / tags (api or web) marks a conversation read (a source-scan test pins the web side); the search text is masked in request logs. No new tenancy exception.
- **Notifications:** `notifications` owns the Telegram link (one per membership, made only by the member through a single-use 10-minute connect link opened with `/start tgi_<token>`), presence leases and the ping ledger. The tab's live socket sends `{type:'presence', on_screen}` frames (inbound limit 1024 bytes; lease = 50 s, extended by the keep-alive); `telegram_link.changed {workspace_id, account_id}` reaches only that account's sockets. `bots` takes an inbound interceptor (`consumed` = not captured) and a bot-connected hook (removes links made with another bot); `sendMemberMessage` + the bot's `send_paused_until` (any rate limit; replies never wait for it). Queues: `notifications.send-bot-message` (+ `-dlq`, retry 2, expire 30 s), `notifications.send-pings` (policy `stately`, `singletonKey` = workspace id, retry 0, expire 60 s; `stately`, not `exclusive`, because `exclusive` refuses the chain's own next link while the sweep is active), `notifications.schedule-pings` (cron every minute). A sweep per workspace every 20 s decides who is pinged: ledger rows are written before the send, per-member transaction under `FOR SHARE` on the membership. Lock order: membership → advisory `connect-links:<ws>` → link row. Codes: `CONNECT_LINK_LIMIT_REACHED`, `TELEGRAM_ALREADY_LINKED`, `PINGS_NEED_WORKING_BOT`. Pings never carry message text or contact names.
- **Broadcasts:** `broadcasts` owns the four tables above; `contacts` owns `contact_bot_reach`, `conversations` owns `broadcast_items`. Any member drafts, edits, groups (≤ 10 000) and duplicates; the draft author or an owner deletes; only owners read the launch confirmation, launch and stop (`OWNER_ONLY`, re-checked under `lockActiveMembers`). Saves carry `expected_version`; a launch carries the confirmation's `version` + `fingerprint` (sorted reachable ids) and freezes the recipients (blocked / never wrote to the current bot left out); ≤ 10 launches per workspace per rolling 24 h. Sending (`broadcasts.send`, policy `stately`, `singletonKey` = workspace id, retry 3, expire 60 s, DLQ `broadcasts.send-dlq` restarts the chain 60 s later; one link ≤ 20 s, ≤ 8 in flight, round-robin turns): the block mark at the turn decides, the claim commits before the send (at most once; a stale `sending` → `not_confirmed`), every send goes through `bots.sendBroadcastMessage` (25 per second per bot, waits for the bot's `send_paused_until`; replies never do), each delivered / not confirmed outcome writes its broadcast item in the same transaction. `broadcasts.measure-blocked-share` (policy `exclusive`, `singletonKey` = broadcast id, retry 2, `startAfter` 48 h) logs the 48 h blocked share. Lock order: launch = memberships `FOR SHARE` → advisory `broadcast-launches:<ws>` → broadcast row `FOR NO KEY UPDATE` → recipient inserts → job; stop / owner delete = memberships → broadcast row; draft, group, abort, finish = broadcast row `FOR NO KEY UPDATE` → its rows; outcome = recipient row → item. Signals `broadcast.changed {workspace_id, broadcast_id, change}` (report changes ≤ 1 per second per broadcast), `contact.changed {change:'reach'}`, `conversation.changed` with item type `broadcast` (`created` only) reach every socket of the workspace; a broadcast item never touches the conversation's state, unread or pings. Text 1–4096 UTF-16 units, name 1–80 graphemes (`packages/shared/src/broadcast-text.ts`), sent plain (no `parse_mode`); text, names and chat ids never in logs, frames or job payloads. Codes: `BROADCAST_NAME_INVALID`, `BROADCAST_TEXT_INVALID`, `BROADCAST_DRAFT_CHANGED`, `BROADCAST_GROUP_CHANGED`, `BROADCAST_NOT_A_DRAFT`, `BROADCAST_NOT_ENDED`, `BROADCAST_AUDIENCE_CHANGED`, `BROADCAST_AUDIENCE_TOO_LARGE`, `BROADCAST_NO_REACHABLE_CONTACT`, `BROADCAST_NEEDS_WORKING_BOT`, `BROADCAST_LAUNCH_LIMIT_REACHED`. Integrity run book: `broadcastIntegrity.*` in `apps/api/src/e2e/helpers.ts`. No new tenancy exception.
- **DB:** one shared `Kysely<DB>` (`src/platform/db.ts`). `DB` is generated into `src/platform/db.types.gen.ts` — never hand-edit it. No triggers or stored procedures; constraints are fine.
- **Migrations:** reversible — every migration exports a working `up` **and** `down`. After migrating, run `pnpm db:codegen` and commit the regenerated types. Destructive changes still go expand → migrate → contract.
- **Contracts:** request/response bodies are zod schemas in `packages/shared`, validated by `fastify-type-provider-zod`; the web client parses responses with the same schemas (`apps/web/src/shared/api/client.ts`).
- **Config:** env vars are parsed only in `src/platform/config.ts`; document every key in `.env.example`. No `process.env` elsewhere. Bot keys: `BOT_TOKEN_ENCRYPTION_KEY` (required), `TELEGRAM_WEBHOOK_BASE_URL`, `TELEGRAM_WEBHOOK_MAX_CONNECTIONS`, `TELEGRAM_API_ROOT` (tests).
- **Telegram:** all Bot API calls go through `telegramApi(token, { apiRoot })` in `src/platform/telegram.ts` (via the `bots` gateway). Each bot's webhook is `POST /api/telegram/webhook/:botId`, authenticated by `X-Telegram-Bot-Api-Secret-Token` (a per-bot derived secret, only its hash stored, checked before the body is parsed; the header is redacted from logs). Bot tokens are secrets — encrypted at rest, never logged, never returned. Tests use the fake Bot API in `src/test/fake-telegram.ts` (scriptable `sendMessage`, `getFile`, file download). Replies go out only via `deps.bots.sendText`, customer media streams via `deps.bots.openMedia` — the token never leaves `bots`.
- **Live socket:** `GET /api/workspaces/:workspaceId/inbox/live` — guarded upgrade (session + membership) with an `Origin` check against `PUBLIC_WEB_URL`; frames are change signals only (clients refetch through the read routes); ping every 25 s, membership + session re-validated every 5 s; close codes 4401 (session ended), 4403 (access removed), 1001 (shutdown). Web client: `apps/web/src/shared/api/realtime.ts` (`openLiveSocket`).
- **Delivery:** `inbox.deliver-replies` (policy `stately`, `singletonKey` = conversation id, retry 3, expire 60 s, dead letter `inbox.deliver-replies-dlq`) drains one conversation's pending replies at most once each (in-flight attempt mark); a Telegram back-off is a new delayed job, not a pg-boss retry; payload is ids only.
- **UI:** compose shadcn/ui primitives from `apps/web/src/shared/ui` (add new ones with `pnpm dlx shadcn@latest add <name>` inside `apps/web`, then check the import points at `@/shared/lib/utils`). Tailwind only — no CSS modules, no CSS-in-JS.

## Tests

- Vitest everywhere; `pnpm test` runs every workspace.
- Unit: `*.test.ts` next to the code — domain + app with in-memory port fakes.
- Integration: `*.int.test.ts` — real Postgres via Testcontainers (`apps/api/src/test/postgres.ts` applies migrations), HTTP via `app.inject()`. Needs Docker.
- Web: `*.test.tsx` with Testing Library.
- Docker-backed suites remove their container and data (tmpfs, `stop()` removes volumes, even on failure); Ryuk stays enabled. After a killed run: `pnpm test:docker:clean` (only `org.testcontainers`-labelled containers).
- Smoke test: `apps/api/src/app.int.test.ts` — boots `buildApp()`, `GET /health` → 200.
